# V3 setup: short guide for agents

If the user asked for the one-message setup, the canonical, checksum-verified flow is in
[beyin.md](beyin.md). This file is a short reference for installing from inside an
unpacked release package or a repo checkout.

When the user asks you to follow this file, work inside the current supported client session. Do not install a new account, API key, Mem0, server or package manager. The shared engine uses only the Python standard library.

1. Use the vault path the user chose. If it is unclear, ask only which folder to use. If a new vault is wanted, create the folder; do not move or delete existing notes.
2. Verify the operating system and a working Python: `python3` on macOS/Linux, `py -3` or a working `python` on Windows. Python 3.11+ is required. If there is no interpreter, in the one-message flow apply the official operating-system route in [beyin.md](beyin.md); do not continue as if it were installed.
3. Run the official release ZIP from the package folder you unpacked (or from the source repo root): `python3 scripts/install_v3.py --vault "VAULT_PATH"`. On Windows, put `py -3` at the start of the same command. The installer takes a local backup and copies the shared engine and the client connections into the vault. For Kiro, use the source release or package that contains the `.kiro/hooks/beyin-v3.json` adapter. It does not install a system service.
4. Check with the installed CLI: `python3 "VAULT_PATH/beyin.py" doctor`. Report errors and skill conflicts openly. Do not say "everything is healthy" without a running service or a real client test.
5. If Codex is used, open a new session in the vault folder, review the new hook definitions through `/hooks` and trust them. Do not write trust hashes by hand; do not use a trust bypass during installation. For Claude, open a new session. In Antigravity, open the vault folder as a workspace and trust the folder; when running headless, use `--add-dir "VAULT_PATH"`. For Kiro IDE or CLI V3, open the vault folder, review the Beyin hooks in the Agent Hooks panel or with `/hooks`, and start a new session ([Kiro setup](docs/v3/KIRO.md)). Verify the connection by asking the model to return the information in a synthetic note only through the hook context. Do not put real private data into test output. For Hermes Agent, a plugin connection is needed instead of hook JSON: apply the link + `hermes plugins enable beyin-v3` + restart steps in `docs/v3/HERMES.md`. For OpenCode there is no trust step; opening OpenCode in the vault folder loads the plugin (`docs/v3/OPENCODE.md`). For OMP there is no trust step either; opening OMP in the vault folder loads the `.omp/hooks/pre/beyin-v3.ts` hook (`docs/v3/OMP.md`). For Pi, review the `.pi/extensions/beyin-v3.ts` extension in the vault folder, approve project trust and start a new session; use outside the vault requires an explicit `--beyin-project-root` scope (`docs/v3/PI.md`).
6. The installer installs the `beyin`, `beyin-doktor`, `beyin-guncelle` and `beyin-kontrol` starter skills. The shared access point for skills is `.agents/skills/`; the Claude counterpart is `.claude/skills/`, the Kiro counterpart `.kiro/skills/`. Existing skills are preserved. For additional skills, import only a directory the user chose, with `skill-import --source "SKILL_DIR"`. If there is a differing change, preserve the user's text and report the conflict.
7. Preserve the existing companion identity. If the Core in a new installation is empty, learn the form of address, the work area and expectations of a thinking partner through a short conversation; record them in the notes with the identity/continuity protocol of the beyin skill. Do not re-onboard an existing user. The installer creates the starter notes only once; they belong to the user and are not overwritten on update.
8. When done, tell the user only the vault path, the working client connections and, if any, the single next step. Do not carry JSON/debug dumps, global settings or personal information into the chat output.

## The limit to explain to the user

Once a note is saved, the file is durable. The index is refreshed at hook points such as session start, message submission and end of turn; no continuous background service runs while the clients are closed. When needed, the installed CLI's `sync` command refreshes immediately. Work results are recorded with a structured receipt; the whole private chat history is not imported on its own.

Simple scalar YAML and JSON frontmatter are supported. Complex YAML produces a visible warning; wrong metadata is not silently extracted. First read the source note to understand the fields you need. A new task is created with `task-create --file TASK_JSON`; the JSON schema is in the installed beyin skill. A source task update uses `task-update` with an expected revision; on a conflict, read the current record.

The optional Jev advisor is not part of the installation: it is off by default, it is only for users who have their own TypeSafe API key, and the installer does not ask about it. The local Laya provider is optional in the same way and runs only in shadow mode (`jev shadow --provider laya`; `jev on --provider laya` is rejected); do not install Laya or PyTorch into Beyin's environment, and if the user wants it, follow the separate setup steps in JEV.md. Do not bring it up unless the user explicitly asks; if they do, `python3 beyin.py jev status` shows the state, and `jev shadow`/`jev on`/`jev off` change it. Do not write the key into the command. Limits: [docs/v3/JEV.md](docs/v3/JEV.md).

Update: `python3 beyin.py update` inside the vault; `update --check` for a check only. Rollback: `python3 beyin.py rollback`. To resume an interrupted update: `python3 beyin.py recover`. On Windows use `py -3`. If there is a conflict on a modified managed file, preserve the user's change; do not get past it with `git reset` or by copying files by hand. When the first clean installation is rolled back, the entry command is also removed; to install again, use the official ZIP installer. Details: [update guide](docs/v3/UPDATE.md).

Platform evidence and remaining verifications: [docs/v3/PLATFORM-TESTS.md](docs/v3/PLATFORM-TESTS.md).

## The user's consumption preference

After installation, if the user wishes, apply the Normal/Economy/Manual preference with the beyin skill. Do not change the default without asking. "Check every 15 minutes" is the minimum interval between local event checks; do not set up a periodic job that calls a model. `beyin.py preferences` shows the current setting. [Preferences](docs/v3/PREFERENCES.md).

After a new installation and after a V3.1 update, the version notice is on by default: at most once a day the GitHub release information is read, no notes are sent, and no automatic installation is done. To turn it off: `python3 beyin.py preferences --update-notifications off`. For old V3.0.2, the first transition is the `python3 beyin.py update` command.
